一、结论
================================================================

确认存在影响训练含义的严重实现错误，不只是超参数选得不好。

最重要的错误是候选索引约定没有统一：Phase2使用按 -32..32 排序的65个稠密候选，所以索引32才是保持原位；但普通训练的不可达节点，以及门控训练的不需要修补节点，仍被监督为索引0。索引0实际上对应沿外法线的负方向移动32像素。

因此，本轮结果应视为“含已确认实现缺陷的开发结果”，暂缓以它作出“全局Transformer方向应停止”的研究结论。更合适的当前状态是：BLOCKED_IMPLEMENTATION_REPAIR_AND_RETRAIN。

这不意味着修复后Transformer一定会优于局部模型。程序确实存在错误，与研究假设最终是否成立，是两件不同的事。

同时确认：主表可以从上传的逐图CSV复算得到，21份训练日志的哈希及最佳epoch记录一致。没有发现主表均值计算错误。但表内算术一致不等于训练目标正确，也不等于已重新验证了图像预测和权重来源。

================================================================
三、P0：保持原位标签被写成向内32像素
================================================================

3.1 候选顺序
证据：E01，radius_sensitivity.py 第19—25行。

dense() 中：
    off = np.arange(-int(geo.search_radius), int(geo.search_radius)+1)

R=32时：
    索引0  -> 偏移-32
    索引31 -> 偏移-1
    索引32 -> 偏移0（保持原位）
    索引33 -> 偏移+1
    索引64 -> 偏移+32

实际调用dense()验证：points[:,32]与原轮廓点完全一致。
这与第一阶段稀疏候选把0位单独放在索引0的约定不同。不同候选布局本身没有错，错误在于标签未同步迁移。

3.2 普通选择器标签
证据：E02，train_local.py 第52—67行，尤其第59—61行。

    fixable = ... min(...) <= 4.0
    keep = F.one_hot(torch.zeros_like(fixable, dtype=torch.long), ...)
    target = torch.where(fixable[..., None], target, keep)

当所有可用候选到GT边界都大于4像素时，注释要求保持原位，但one_hot的类别是0，而不是32。

合成复现：构造一个有轮廓节点，65个候选全部有效且距离均为10像素。对65个零logit求梯度：
    梯度最小、梯度下降会提高的类别：0
    期望类别：32
    第0类梯度：-0.9846154
    第32类梯度：+0.0153846

即程序明确奖励-32像素移动，并惩罚真正的保持原位。

影响范围：local和local_large直接调用该损失；local8、medium32、global从train_local导入同一函数。因此普通训练的5个模型族、每族3个种子均走这条错误路径。Transformer还读取同种子局部模型的候选分数，因此不能仅重训Transformer而保留旧局部评分缓存。

3.3 门控选择器标签
证据：E03，train_gated_refiner.py 第22—41行，尤其第25—32行。

门控标签计算中正确使用了索引32作为零位：
    other[...,32] = False
    zero_distance = distance[...,32]

但不需要修补时的候选标签却写成：
    zero = F.one_hot(torch.zeros_like(repair, dtype=torch.long),65)

因此gate分支在学“保持”，candidate分支却在学“-32像素”。这影响local8_gate和global_gate的6个训练流程，而且触发范围不仅是GT不可达节点，也包括原轮廓已经正确的节点。

合成复现：原位置到GT距离为0，其他候选距离为10。
    gate标签：keep（求梯度方向正确）
    candidate标签：0（错误，应为32）

evaluate_gated.py推理时又使用32表示keep，并排除32后选择非零proposal。因此训练目标与推理语义不一致。

由此，现有“阈值必须调到0.95、最后所有节点都不移动”的现象，不能被当作显式门控机制本身无效的干净证据。错误标签可能参与造成这一现象，但不能声称它就是唯一原因。

3.4 错误标签还可能落在无效候选上
证据：E02中的masked_fill和target构造，T01。

靠近图像边缘时，索引0对应的-32像素位置可能不在可见范围内。代码将该类logit固定成-10000，但错误keep标签仍在该类上分配概率1。

合成复现：第0类无效，其他64类有效，所有候选不可达，原始logit均为0。
    当前损失：10004.1592
    正确keep标签损失：4.158883
    第0类原始logit梯度：0（被masked_fill截断）
    有效logit梯度之和：+1

准确含义：优化器不能通过提升该无效候选的原始logit来匹配标签，反而会推动有效logit整体降低。不要把这个数值解释成真实训练数据的平均损失，也不要把有限-10000屏蔽称为数学上绝对不可降低的损失下界。

修复要求：
A. 统一候选offset与zero_index来源，不让每个文件自己猜0位。
B. 当前固定R32布局的最小修复是用torch.full_like(...,32,dtype=torch.long)。
C. 对所有has_contour节点断言零位候选有效，且target在无效候选上的总概率为0。
D. 单测必须覆盖：GT不可达、原轮廓正确、需要修补、候选出界、无轮廓。
E. 旧训练权重和候选分数不能只重新评估，必须按依赖链重训。

================================================================
四、P1：StrongLocal并不是新增网络仅有9×9信息范围
================================================================

证据：E04，local_model.py 第8—29行。

四个卷积块都在完整[B,C,256,256]特征图上应用GroupNorm。GroupNorm按组统计包含空间位置的均值、方差；它在训练与评估时都使用当前输入统计。因此远处特征变化会影响当前位置的归一化值。

本次测试刻意不重跑冻结CNN，而是固定输入特征图，只改动距离候选区域很远的左上角32×32区域：
    候选区域：x=96..160，y=128，保持不变。
    含GroupNorm的原模型：最大候选logit变化0.2508416。
    仅将GroupNorm替换为Identity的同权重对照：变化0。

这说明非局部依赖由新增局部模型本身引入，不只是README已经承认的冻结CNN特征可能包含全图信息。

影响解释：
1. 不能严格宣称“纯局部9×9模型超过全局Transformer”。
2. GroupNorm只是全图统计通路，不等同于充分的全局形状理解，不能据此宣称它已经解决了全局问题。
3. 这并不自动使local8与global的相对比较失去意义，因为二者共享相同局部分数输入；它主要限制“纯局部”解释。训练标签错误则是另一项独立问题。
4. 即使去掉GroupNorm，双线性采样非整数位置也会混合邻近卷积输出，严格的原特征像素依赖范围不总是恰好9×9。

修复选项：保留现有结构但准确命名为“局部卷积+全图统计归一化”，或者新增严格局部对照，例如按每个空间位置仅跨通道归一化，或先裁patch后仅在patch内归一化。比较信息范围时应做远处扰动不变性测试，而不只数卷积层。

官方参考（本次已查阅）：PyTorch GroupNorm文档说明分组统计及train/eval均使用输入统计；具体远处依赖由本次调用源码的测试直接证明。

================================================================
五、P1/P2：其他应修复或限制解释的问题
================================================================

5.1 wrong_move_rate把任何已正确节点上的移动都计为错误
证据：E12，evaluation.py 第48—56行。

    correct = d0 <= 2
    wrong_move_rate = (moved & correct).sum() / correct.sum()

该指标没有判断移动后更好还是更坏。
合成例子：移动前距离1.5像素，移动后0.5像素。
    repair_precision = 1
    wrong_move_rate = 1

不是所有“已接近GT的节点移动”都是真正损害。该字段可以保留但应改名为move_rate_on_initially_correct；另报distance_increase_rate和correct_to_incorrect_rate。keep_accuracy当前更像已正确节点的保持比例，也不应盲目要求它最大。

此问题影响机制指标和“过度修补”解读，不会直接改写Dice或训练损失。

5.2 DP不是完整65候选空间上的最优解
证据：E13，evaluate_local.py 第26—43行。

当前先按原始logit选8个非零候选，加上零位，再加入位移惩罚做DP。剪枝本身已有披露，不应误称为DP递推bug，但有两个限制：
A. 65候选Oracle和9候选学习式DP的搜索空间不同。
B. 惩罚加入之前剪枝，可能删掉最终代价最好的近距离候选。

合成复现：8个远距离候选偏移-32..-25，原始分数2.0；偏移+1的分数1.9；alpha=0.1，lambda=0。
    完整65候选的最优选择：+1。
    当前剪枝后的选择：0。

建议至少按加入位移代价后的分数剪枝，补一个完整候选或更大候选数的DP对照，并报告剪枝后的GT可达性。即使这样，带相邻平滑项时局部top-K也仍是近似，不能保证保留全局最优路径。

部分DP控制选中lambda=0.2，即搜索网格上边界（例如seed17的local、local_large、global均如此；并非所有9组都取上边界）。因此不能统一声称各组简单DP都已充分优化，应对触及边界的配置在开发集检查更大的lambda或自适应扩展范围；不要用test调整。

5.3 新缓存从零构建后，正式训练入口反而会拒绝
证据：E07—E11。

build_feature_cache.py现在已正确用load_mask(...)[0]取256×256 GT，并做形状及面积检查。但是输出COMPLETE.json时没有写gt_shape_verified_for_all。
train_local.py第102—103行要求该字段等于2150，否则抛出异常。
历史repair_gt_cache.py会写入该字段，但该脚本第35行只接受旧的全零GT缓存，已经修复的全新缓存不能再走这条迁移路径。
另外audit_phase2.py只接受'repaired complete 2D official GT mask'，而新的build_candidate_cache.py写的是'complete 2D official GT mask'。

这是明确的构建器/消费者元数据契约不一致。它不证明已发布训练一定失败，因为存档中的历史修复缓存确实含有所需字段；它证明README建议的从零构建流程不能原样顺畅复现。

最小修复：在完成实际GT检查后由新构建器写入gt_shape_verified_for_all=n；审计器接受经过验证的新建与迁移两种来源。不要为了过审随意手工填PASS。最小补丁已包含这两项。

5.4 全部keep并不严格等于原CNN掩码
证据：E25—E26，T01、T02。

零位是重采样后的256个轮廓节点；将这些点用直线闭合并栅格化，本来就可能改变少量像素。
存档gate结果没有移动任何节点，但在val100上：
    CNN Dice：0.8530507409
    全部keep重建 Dice：0.8530754762
    29张图的Dice与CNN有非零差异
    平均差值：0.0000247353

这属于重建近似和对照定义问题，不是训练标签索引错误的另一种表现。当前均值影响很小，不能拿它解释全部模型差距。

应补上Phase2自己的G1零位重建基线，分开报告“重建引起的变化”和“学习移动引起的变化”。若keep被定义为严格不改输出，应统一推理入口并在全部keep时直接返回原mask；仅修改selected_mask()不够，因为几个评估脚本直接调用rasterize/compose。

5.5 参数匹配是单个refiner模块匹配，不是完整新增系统匹配
证据：E04—E06，T01。

    StrongLocal小模型：137,217
    LocalLarge：291,841
    NodeRefiner：287,425
    StrongLocal小模型 + NodeRefiner：424,642

NodeRefiner需要先训练的小局部模型给出65个候选分数。完整方法报告参数与推理成本时不能漏算这一模块。可以区分“当前阶段可训练参数”和“全部新增已学习参数”。局部/中程/全局三个Transformer本身参数完全匹配，这一点没有发现错误。

5.6 val100不是本轮独立验证集
证据：E15、E18、E19、E27及上传的split_provenance。

alpha按cal50选择这一逻辑正确，但局部模型和Transformer已经在整个val150上选择最佳epoch，因此val100在本轮本身也参与过模型选择，并不只是历史第一轮被查看过。
README已经披露开发数据复用及上游CNN的潜在val暴露；这不是本次新发现的隐瞒式数据泄漏。准确结论仍应是开发集观察和探索性区间，不能当独立测试。

5.7 Oracle目标与训练目标并不相同
证据：E23—E24。

训练用GT内侧边界像素EDT双线性采样；Oracle用到GT亚像素0.5等值线线段的精确欧氏距离，且再做闭环DP。二者不是相同监督下只差一个选择器。
这是已选代理目标，不必直接判为bug。但Oracle与学习器之间差距不能全算作Transformer可学习、可填补的空间。应增加与训练标签完全一致的EDT-Oracle来分离这项影响。

5.8 阶段A的dense recall@K不是按置信度排序的recall@K
证据：E29—E30。

稠密候选在该脚本中是“0位在前，剩余非零偏移按坐标顺序排列”，统计又直接取前K列。因此dense recall@K在不少K下偏向一侧，不是得分最高K个候选的召回。完整candidate coverage不受此命名问题影响。
应明确“first-K under fixed ordering”，或在GT无关评分下排序后再计算top-K recall。

================================================================
六、已经核实、暂未发现所述类型错误的部分
================================================================

6.1 当前二维GT读取已修复
build_feature_cache.py使用[0]，不是旧的[0,0]。历史空GT问题有修复记录，存档元数据也有2150张形状检查记录。不能因为仓库存在invalid_local_training_repair.json就断言当前正式结果还在使用全零GT。尚存的是新的keep标签错误。

6.2 注意力布尔mask没有写反，也不是local/global实际上完全相同
证据：E05。
环形距离构造正确，True表示禁止注意力。每层可直接访问节点数：local8=17，medium32=65，global=256。
两层叠加后的图上可达节点数：33、129、256，分别约对应±16、±64和全局。
因此“±8/±32”应说成每层窗口，不是整网最终信息半径。这里并未发现核心mask实现错误。

6.3 GT没有直接传入普通模型的特征前向
节点context来自CNN特征、RGB、概率图、边界概率和预测几何；gt_distance用于损失和机制评估。候选几何来自CNN预测。静态调用链未发现使用GT交点来筛选普通推理候选或GT直接拼入输入。上游训练集暴露和历史访问不在这项静态保证内。

6.4 冻结CNN与边界头评估模式
FrozenMSGUNet将参数requires_grad设为False，并覆盖train()保持eval；边界头加载后调用eval。未发现本轮在修补器训练时误更新冻结CNN的路径。

6.5 Split与记录一致性
split中的train=2000、val=150、test=600，集合两两交集为0，三个文件哈希均与存档一致。特征缓存元数据列出2150条train/val记录，没有test记录。
这支持本轮源代码的test封存设计，但不等于独立验证所有历史访问从未发生。

6.6 指标和主表算术
Dice、IoU和BF1基础公式及合成同掩码/空预测测试通过。BF1容差是256×256输入坐标上的2像素。
三种子逐图CSV聚合与每个种子的summary一致，最大差为0；总均值也在浮点误差范围内一致。候选coverage和Oracle均值的表内复算一致。
HD95实现采用两个有向95分位数的较大者，ASSD按两侧边界点数加权；这属于明确实现口径，不应在没有比较标准的情况下直接判错。单侧空掩码用图像对角线有限惩罚，像素precision空预测取1，均需在正式报告中写清，不可与其他口径混用。

6.7 闭环DP递推
20组4节点×3候选的合成问题，与81条路径逐一穷举比较，最大目标误差0。发现的是前置剪枝限制，而不是当前这组测试下的闭环递推错误。

6.8 日志存档
21份训练日志的文件SHA256与training_manifest一致；每份记录的最佳epoch与CSV中最低val_loss所在epoch一致。
权重文件未包含在ZIP内，不能进一步证明best.pth与日志、源代码和预测完全一致。

================================================================
七、现有结果哪些可以保留，哪些需要重做
================================================================

可保留作开发诊断：
A. 冻结CNN与split记录，前提是实际缓存/权重哈希复核通过。
B. 阶段A候选数量、峰值筛选及搜索范围诊断；其计算路径不依赖本次学习损失的keep标签。

八、建议的最小修复与复验顺序
================================================================

第一步：冻结旧版本并标记实现阻断。
保留当前所有结果，新增版本目录。报告状态改为需要实现修复和重训，不进入正式test。

第二步：修复标签和缓存契约，先运行小测试。
统一zero_index，校验target只分配给有效候选，检查GT不可达与本来正确节点必须标记keep。增加方向符号、边界裁剪、无轮廓以及新缓存从零构建测试。

第三步：统计真实标签分布，不直接扩模型。
在train/val分别记录：不可达节点比例、keep/repair比例、旧目标落在无效候选上的比例、偏移-32/+32/0的标签与预测比例、按距离或病灶大小分层的情况。
这些统计能量化本次bug在真实数据中的规模。本ZIP缺少缓存，所以本审计没有编造这些比例。

第四步：决定严格局部对照的定义。
保留GN时准确改名；研究信息范围时至少增加一个没有新增跨空间归一化的对照。两种情况下都保留相同候选和基础特征，并用远处扰动测试验证。

第五步：先重训seed17的四个核心组。
建议依次：StrongLocal小模型、LocalLarge、local8、global。先确保局部模型有效、分数缓存更新，再训练注意力。可先做少量训练图像的过拟合/梯度调试，但soft target交叉熵有标签熵下界，不要错误要求其趋于0；可同时监控KL和候选距离。

第六步：重新校准且补对照。
补G1零位重建；完整或更大候选数DP；更合理的lambda搜索；修正wrong_move指标；必要时做与训练标签一致的EDT-Oracle。

第七步：仅在基本链路通过后扩到三种子和门控。
若修复后的global仍未超过强局部与local8，应接受这一负结果，再讨论调整方向。若确实出现稳定优势，随后在干净、未用于开发的独立集进行一次确认。

不建议现在跳过修复继续增加模块，也不建议立即跑官方test来决定是否保留方法。

    python reproduce_audit.py --repo "D:\path\skin--main" --out audit_results.json
    python check_archived_results.py --repo "D:\path\skin--main" --out archived_result_checks.json

最小补丁必须先在新的工作分支审阅；在仓库根目录可用git apply --check检查适用性。补丁不是完整科学修复方案，不包含重训结果。
本审计没有改动上传仓库原文件，也没有覆盖旧实验结果。
